# Cloud pending op transitions

Generated by `test/cloud_transitions_test.dart` from `transition` and `entryViews` in `lib/src/cloud/queue.dart`. Run with `UPDATE_TRANSITIONS=1` to rewrite.

Each section builds a queue by real events until op `x` is in that state, then applies one event. The state and its holds are derived from the stored facts after every event. Events that do not apply are listed after the table; the queue is left as it was.

## Who decides

- The server's answer to an op is the only thing that takes it out of the queue or hands it to the user. Applied or nothing to do: done. Rejected: the user decides, and later work on that row waits behind it, unless the row the rejection carries already holds what the op wrote, which never applies to `row_replaced`: that row is another life of the row, so the op is not delivered whatever its value. Failed: the user decides.
- When the user gives up an entry (takes the cloud's version or discards it), every later entry for the same row, page or strategy goes with it, because it was built on the work given up.
- Results (the rows the server sent) never settle or drop an entry. They end the drawing of landed work, and they tell a whole-row write whether its row is as the user saw it. Two results also stop sending: the page delete below, and a result saying the strategy is gone, which stops every claim for that strategy.

## Which revision an op names

An op names the revision the user's edit was made against. The device keeps, per row, a justified row: a revision with the content at that revision, compared by content for every row, the strategy included. Nothing is justified when a session opens. A row becomes justified when a result of this session shows it, or when this device's own op on it is answered at exactly the revision `applyOp` predicted over a base that was already justified when the edit was made: either the row a queued edit ahead of it predicted, or the justified row itself. An answer of nothing to do at the justified revision of an op that changes nothing keeps the row justified. Any other answer, nothing to do at another revision included, means someone else wrote in between: the row is not justified until a result shows it, and every later edit of that row loses its justification too. A result never changes the revision an op names. `_judge` in `lib/src/cloud/queue.dart` is the only place an outgoing revision is chosen.

- An op made with nothing of this device's ahead of it on its row goes at its authored revision, and the server decides.
- A field merge that stays on its page names its fields and goes at its authored revision once no earlier edit of this device on that row is still unanswered; this device's landed work on the row never holds it, and the server merges it field by field. A merge that names another page is written whole by the server, so it is gated like a whole-row write.
- Any other op made behind this device's queued or landed work on its row, a nothing-to-do answer included, goes only once that row is justified at the revision it names, with the content the user saw (or already holding what the op writes). Otherwise it waits for the row's result, and needs the user when a result of this session shows the row otherwise, when a result of its page no longer holds a row that results showed or this device added, or when its page is gone.
- A page add, reorder or delete answers only the strategy revision, so the pages it renumbers are not justified by the answer: a page rename behind one waits for a page list.
- An undo of a delete goes without asking only over this device's delete answered at the revision it predicted, with the tombstone as the user saw it, within 29 days of first sending that delete.
- An entry that carries a revision check and was written more than 29 days ago needs the user before it is sent, sent before or not, because a purged tombstone can come back at revision 1.
- Keep mine names the revision the user chose theirs over.

## The resend window and the sender

- An answer that never came is sent again under the same op id, in checked form, until 29 days after the op was first sent; the server remembers answers for 30. A batch refused whole (upgrade, sign-in, access) was never tried, so it does not start that clock, even when the refusal arrives after the attempt was given up. A transition that finds the 29 days passed records it, even when it changes nothing else; views show only what was recorded, and `look` records and returns the views of the queue it returns. Once recorded, the entry waits for the user and is never sent again.
- The queue cannot stop a send it already handed over. The sender must give an attempt up as unanswered (`TransportFailed`) within `sendGiveUpAfter` (one hour) of claiming it, well inside the one-day margin between the queue's window and the server's memory. An open attempt shows as sending until the sender does so.
- Answered work that the latest results do not show yet is drawn as landed, in the order the server applied it, off its source page and on its destination, until a result shows that row at the answered revision or later, or until a result about the page its op names, at or after its answer by order and server time, shows that page gone: that page's own page-gone, or a list newer than the page's own result that no longer has it. An item edit that names no page is not retired this way, as an answer names a revision and not where the row is. A result about another page never retires work, and while the strategy itself is gone nothing retires. A delete this device made stays known as its own until a result shows a later revision of the row or its page is gone that way. An undo onto a page that is gone asks the user, with that reason, whether or not this device's delete is still drawn.

## Which copy of a row a result leaves held

- `Shown.taken` decides once, for every row a result carries, whether it replaces the copy held, and names every row the result removes. The store writes what it decides and nothing else. A row replaces the held copy unless the held copy is newer: lives compare first when both are known, revisions otherwise. A row without a revision never replaces one with a revision. A taken row whose stored copy already has the same contents is not written again. One removal can cover several stored rows: a page leaving takes its page row, its settings and every item on it, damaged ones included.
- Every result carries a stamp: the client, the connection, the snapshot and the server time. Its order is the session, then the client, then the snapshot. `taken` is never given a result older than one already taken for the same page or the same list. `resultFit` in `lib/src/cloud/queue.dart` drops those as `OlderResult` before any row is compared. A result at the order already taken is the same answer: it pays what it would have paid and changes no content, and one whose content differs is reported (`ReportSameOrderDiffers`) and changes nothing. A page's taken order is about the results seen for that page: a list that removes the page leaves it as it was, and only a new session drops it.
- Which pages exist is decided by the newest claim about that page, whatever kind of result made it. A list claims, for every page, that it is live, trashed or absent; a page's own result claims live or trashed (`PageRead`) or gone (`PageGone`). The newer claim by order wins, and a claim older than the other kind's claim for that page changes nothing about existence. So a list removes a page it does not list only when that page's own result is older than the list or there is none, does not bring back a page whose own newer result says it is gone, and sets a listed page live or trashed only over an older own result. A `PageGone` older than the list taken is dropped as `OlderResult`, and so is a `PageRead` older than a list that does not list the page; a `PageRead` older than a list that lists the page gives its items and nothing else. A list and a page result at the same order that disagree about whether the page exists are reported (`ReportSameOrderDiffers`) and leave that page as held; the rest of the list still applies.
- Each kind of row has its sources. The list carries the strategy row and the settings rows: a list writes the settings of every page it lists, under the version rule above, so a settings row at a lower revision than the one held is kept out. Page rows come from both kinds: a page's own result newer than the list writes that page's row whole, its place in the list included, so until the next list two pages can show the same place; that list sets every page row it decides. A page's own result owns that page's items, ordered by that page's taken order. A list that adopts a later strategy life starts from nothing: no taken or refused order of the old life is kept.
- A mark advances only with the content applied for its subject; a refusal, a dropped result, or a result about another subject moves none. A read refusal keeps its own order for its subject: it is dropped when it is not newer than the content taken there or is older than the last refusal taken, and the first result at a refused point is taken. A read refusal replaces only an order owed, and only with its own order; any other debt stays as it was.

## When the stored base disagrees with the queue

The queue's record (`Shown`) and the stored rows must agree. When a strategy's queue loads: its strategy, page and settings rows, and which items are stored on which page. When a page loads, before any of its rows is used: each item's page and version, and in checked builds its contents against a digest this run computed. Two rows agree when their name, page and version match, whether or not this build can read their contents. A damaged row (one that does not parse as a placed row) never agrees. Rows of a kind this build does not know are left out. After a restart two differences pass the page check: contents changed at the same version, found only when a result for that row arrives (and refused there in checked builds), and a damaged payload in a row that still parses as placed, counted as damaged on its page. No decision is ever made from unchecked rows. A strategy whose queue cannot be read makes no decisions at all: no result is taken and no work is committed, and its rows are shown unchecked and marked held, as before this check. The only writes made in that state are the ones the user explicitly chooses: discarding the unreadable queue, which removes the base rows and owes the page list, and removing the strategy.

The stored results (`read/header` and `read/page/…`) are the one part of the queue that does not hold the strategy when this build cannot read it, whether a newer build wrote it in a shape this one does not know or the row is damaged. When any of them cannot be read, and nothing else of the queue is unreadable, the load drops all of them, since they mean something only together, and rebuilds `Shown` from the stored base rows: the strategy, page and settings rows, every stored item on the page it is stored on, the contents of each live page that holds items, and the highest version of each row at the version stored. Nothing is read this session: no debts, no results taken, no marks. The rows-agree check then runs against what was rebuilt and passes unless a row is damaged or an item is stored on two pages or on a page with no page row, which refuses the strategy as before and writes nothing. Otherwise one commit at load removes every stored results row and writes the rebuilt ones in their place, leaving the base rows, entries, attempts, landed work and strategy facts byte for byte as they were, and the sender reports it once. What the dropped rows held that the rebuild does not: debts, which a later session pays (every result after the restart is one, and a read labelled with the ended session is refused); versions of rows no longer stored, which only matter against a page list or page result read this session, and are raised again by it; and contents for a page read with no items, which the sender reads again, a copy of that page being refused until it has. Work a dropped debt held waits no longer for it: it was written in an earlier session, so it goes out checked, at its revision and naming the strategy and row lives it was written over, and the server refuses it if the row or the strategy was replaced, which owes the read again. Work that needs a result read this session (a held page delete, a whole-row edit behind our own work) waits for it as after any restart, and landed work stays drawn until a result shows it. A queue entry, attempt, landed work or facts row this build cannot read still holds the strategy, and so do stored results beside it. `test/cloud_results_dropped_test.dart` covers each of these.

A disagreement refuses the strategy: nothing is written, no result is taken, the reader does not show it, and the sender neither reads nor sends for it and reports the reason once. Queued work stays on disk as it was. How a refused strategy gets its copy back is decided before the store is switched on for users (#819).

Nothing about the refusal is stored. A disagreement found in this session refuses that strategy from the load that found it until the store closes, or until the strategy's stored rows are removed from this device or written afresh (the strategy removed, its rows found gone, its unreadable queue discarded, or the strategy added to the store again); it is never written to disk and is consulted only to refuse that strategy's open. After a restart the open passes the queue-load check when the fault is on a page. A fault the page check finds refuses the strategy again as soon as that page loads, whether a reader, a result or the summary loads it first; the two differences that pass the page check after a restart (above) are found only as said there, or not at all. Each refusal the store makes carries a serial that only grows for the life of the store instance and is never stored; the sender reports each serial once, and a sender that starts later asks the store for the refusals standing then. A queue load can refresh the sync tally shown in memory before a page check refuses the strategy, so the summary shown can change although its saved bytes do not.

- When a page result leaves out an item the device held there, the item is marked with that result's read order and the version last held. A later-arriving result whose read started before that order, carrying the item at that version or older, does not bring it back; a newer version always does. Marks are kept in memory and end with the session. `test/cloud_row_decision_test.dart` covers both ("a page result read before another page removed an item stays out when it carries the version last held, and is taken when it carries a newer one").
- One case is taken although it may be stale. The device holds an item on page A. On the server it moves to page B, and a read of B starts. While that read is in flight, the item moves back to A, is deleted, and is purged by the server. A read of A that started after the read of B arrives first and leaves the item out. Then the read of B arrives carrying the item at a version newer than the one last held, so nothing shows it is stale, and the item is shown on B. A purged row has been deleted for a long time, so all of this has to happen while one read is in flight. The next read of B removes it. A read of the same page that started before the removal is dropped whole as older. The same case arises without the move back when the device never saw the move to B: the read of A leaves the item out, and an older read of B arrives after it carrying the item at a version newer than the device held. It is taken for the same reason and corrected the same way.

## Folding

A field edit folds into an earlier field edit of the same row only when the earlier one is unsent and unclaimed, both name exactly the same fields, and nothing else for that row is queued between them. The folded edit is not exactly the two sent in turn in two corners:

- The server already holds the first edit's value. Sending both is a no-op then an applied edit; the folded edit is a field conflict and needs the user, with the server's value and the user's value both kept.
- The server already holds the later edit's value where the first would conflict. Sending both holds the first for the user; the folded edit lands and the server ends at the user's last value for every field it names.

`test/cloud_fold_test.dart` requires every other case to give what sending both gives.

## The page delete exception, until #670

The server guards a page delete by the strategy's revision only, so a page delete can land after a teammate changed the page ([#670](https://github.com/SunkenInTime/icarus/issues/670)). Until the server checks the page itself, one rule decides a page delete, with no partial cases. It is decided only when the device holds a page list and a result of that page, both taken in the current session and both current for that page. Every answer of this device, whatever it says, leaves a mark: on every page its op touches (both ends of a move), on the page list when it changes the list, on every page when it renumbers pages, and on the row it wrote. A result meets a mark when it is at or after the answer in order and, if the answer carried a server time, at or after that time; it also meets it when it shows the row the answer wrote at the answer's revision or later. Marks of several answers on one subject combine: the latest order and time, and the newest revision written of each row, so a result showing every one of those rows at that revision or later meets them all, and one answer that wrote no row leaves only order and time. A page's result is current when it meets the marks on that page, on every page, and on every row it shows now, wherever the row was when the answer came; the page list is current for a page when it meets the list's marks and that page's. Marks live in memory: a session opening keeps them, a restart drops them. Until then it waits, and `resultsNeeded` asks for whichever of the two is missing. Then: if the page list says the page is gone, the delete goes and the server answers; the page's own result is not needed then, since it cannot change the outcome. Otherwise the page (its name, its settings, and the rows on it by id and content, leaving out a row a result shows on another page) is compared with what the user saw: equal means the delete goes, anything else means the user is asked. Both results arrive after every answered op of this device's that touches the page, so they already include its landed work. A delete with nothing ahead of it on a page already read this session goes at once; a delete queued behind this device's own work on that page waits for the page list and the page to come round once more after the last answer. That wait is deliberate and goes away with #670. A current page list newer than the page's own result that leaves the page out settles it as gone. Otherwise a page list and a page result that disagree about whether the page exists are no verdict: the delete waits and asks for both. For a page delete the hold's verdict that the page is gone comes before the revision check, and a page delete queued behind other entries asks for nothing until it reaches the head. All of this lives in `lib/src/cloud/held_page_delete.dart` and comes out in one piece when #670 lands.
