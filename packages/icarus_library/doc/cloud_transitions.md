# Cloud pending op transitions

Generated by `test/cloud_transitions_test.dart` from `transition` and `entryViews` in `lib/src/cloud/queue.dart`. Run with `UPDATE_TRANSITIONS=1` to rewrite.

Each section builds a queue by real events until op `x` is in that state, then applies one event. The state and its holds are derived from the stored facts after every event. Events that do not apply are listed after the table; the queue is left as it was.

## Who decides

- The server's answer to an op is the only thing that takes it out of the queue or hands it to the user. Applied or nothing to do: done. Rejected: the user decides, and later work on that row waits behind it, unless the row the rejection carries already holds what the op wrote. Failed: the user decides.
- When the user gives up an entry (takes the cloud's version or discards it), every later entry for the same row, page or strategy goes with it, because it was built on the work given up.
- Results (the rows the server sent) never settle or drop an entry. They end the drawing of landed work, and they tell a whole-row write whether its row is as the user saw it. Two results also stop sending: the page delete below, and a result saying the strategy is gone, which stops every claim for that strategy.

## Which revision an op names

An op names the revision the user's edit was made against. The device keeps, per row, a justified row: a revision with the content at that revision, compared by content for every row, the strategy included. Nothing is justified when a session opens. A row becomes justified when a result of this session shows it, or when this device's own op on it is answered at exactly the revision `applyOp` predicted over a base that was already justified when the edit was made: either the row a queued edit ahead of it predicted, or the justified row itself. An answer of nothing to do at the justified revision of an op that changes nothing keeps the row justified. Any other answer, nothing to do at another revision included, means someone else wrote in between: the row is not justified until a result shows it, and every later edit of that row loses its justification too. A result never changes the revision an op names. `_judge` in `lib/src/cloud/queue.dart` is the only place an outgoing revision is chosen.

- An op made with nothing of this device's ahead of it on its row goes at its authored revision, and the server decides.
- A field merge that stays on its page names its fields and goes at its authored revision once no earlier edit of this device on that row is still unanswered; this device's landed work on the row never holds it, and the server merges it field by field. A merge that names another page is written whole by the server, so it is gated like a whole-row write.
- Any other op made behind this device's queued or landed work on its row, a nothing-to-do answer included, goes only once that row is justified at the revision it names, with the content the user saw (or already holding what the op writes). Otherwise it waits for the row's result, and needs the user when a result of this session shows the row otherwise, when a result of its page no longer holds a row that results showed or this device added, or when its page is gone.
- A page add, reorder or delete answers only the strategy revision, so the pages it renumbers are not justified by the answer: a page rename behind one waits for a page list.
- An undo of a delete goes without asking only over this device's delete answered at the revision it predicted, with the tombstone as the user saw it, within 29 days of first sending that delete.
- An entry that carries a revision check and was written more than 29 days ago needs the user before it is sent, sent before or not, because a purged tombstone can come back at revision 1.
- Keep mine names the revision the user chose theirs over.

## The resend window and the sender

- An answer that never came is sent again under the same op id, in checked form, until 29 days after the op was first sent; the server remembers answers for 30. A batch refused whole (upgrade, sign-in, access) was never tried, so it does not start that clock, even when the refusal arrives after the attempt was given up. A transition that finds the 29 days passed records it, even when it changes nothing else; views show only what was recorded, and `look` records and returns the views of the queue it returns. Once recorded, the entry waits for the user and is never sent again.
- The queue cannot stop a send it already handed over. The sender must give an attempt up as unanswered (`TransportFailed`) within `sendGiveUpAfter` (one hour) of claiming it, well inside the one-day margin between the queue's window and the server's memory. An open attempt shows as sending until the sender does so.
- Answered work that the latest results do not show yet is drawn as landed, in the order the server applied it, off its source page and on its destination, until a result shows that row at the answered revision or later. A delete this device made stays known as its own until a result shows a later revision of the row.

## Folding

A field edit folds into an earlier field edit of the same row only when the earlier one is unsent and unclaimed, both name exactly the same fields, and nothing else for that row is queued between them. The folded edit is not exactly the two sent in turn in two corners:

- The server already holds the first edit's value. Sending both is a no-op then an applied edit; the folded edit is a field conflict and needs the user, with the server's value and the user's value both kept.
- The server already holds the later edit's value where the first would conflict. Sending both holds the first for the user; the folded edit lands and the server ends at the user's last value for every field it names.

`test/cloud_fold_test.dart` requires every other case to give what sending both gives.

## The page delete exception, until #670

The server guards a page delete by the strategy's revision only, so a page delete can land after a teammate changed the page ([#670](https://github.com/SunkenInTime/icarus/issues/670)). Until the server checks the page itself, one rule decides a page delete, with no partial cases. It is decided only when the device holds a page list and a result of that page, both from the current session and both received after this device's last answered op that touches that page or the page list; until then it waits, and `resultsNeeded` asks for whichever of the two is missing. Then: if the page list says the page is gone, the delete goes and the server answers; the page's own result is not needed then, since it cannot change the outcome. Otherwise the page (its name, its settings, and the rows on it by id and content, leaving out a row a result shows on another page) is compared with what the user saw: equal means the delete goes, anything else means the user is asked. Both results arrive after every answered op of this device's that touches the page, so they already include its landed work. A delete with nothing ahead of it on a page already read this session goes at once; a delete queued behind this device's own work on that page waits for the page list and the page to come round once more after the last answer. That wait is deliberate and goes away with #670. Every answer, whatever it says, resets the results of every page its op touches (both ends of a move) and, when it touches the page list, the list for every page. A page list and a page result that disagree about whether the page exists are no verdict: the delete waits and asks for both. For a page delete the hold's verdict that the page is gone comes before the revision check, and a page delete queued behind other entries asks for nothing until it reaches the head. All of this lives in `lib/src/cloud/held_page_delete.dart` and comes out in one piece when #670 lands.
