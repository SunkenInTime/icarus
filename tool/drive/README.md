# Driver runs

A driver build is the desktop app with `lib/dev/drive/drive.dart` compiled in. It plays a JSON script from `scripts/` the way a user would and writes a log that ends in `SUMMARY ... CLEAN` or `SUMMARY ... PROBLEMS`. The steps are listed at the top of `lib/dev/drive/drive.dart`.

A run passes only when every instance finished its script with `SUMMARY ... CLEAN` and quit before the timeout. The Linux runner also needs the app's exit code to be 0. `run.ps1` doesn't check it, because Windows builds don't report a trustworthy one. Flutter errors, items drawn away from their saved positions, failed steps and cloud work that never settles all fail it.

## Tapping by text, key or icon

`tapText`, `tapKey` and `tapIcon` tap a match only if a person pressing its middle would press that match: the press must be inside the window, and the first thing under it that takes a press must be the match's own handler or sit inside the match. A handler is something that listens for a pointer going down (a gesture detector, button, text field or modal barrier) and lives inside a route or an overlay entry; a listener that only follows the pointer, or one above the root navigator that watches the whole app, is nobody's control. A match with no handler of its own counts when the first thing hit is the match or inside it.

So a library tile under the editor, a label under the quick switcher's dismissal area, a control that is offstage or under `AbsorbPointer`, a row the list has clipped, anything off screen, and a disabled control (whose own handler never gets the press) are refused. `nth` counts only the matches that can be tapped. A refusal says how many matches were found, how many can be tapped, which one was asked for, and what would take the press instead (or that the match is off screen). When the match tapped is not the one at the same place in the tree, the log says so in a `TAP` line.

To press a disabled control on purpose, as a person can, add `"disabled": true` (`{"tapText": "Delete", "disabled": true}`). The step then presses the match only if the press reaches the handler right around the match's own handler (its wrapper, such as a press animation), the match's own handler is not reached, and the match is drawn there: nothing between it and that wrapper is offstage, and the point is inside every clip between them. It fails if the control is enabled after all, and fails as covered if something else is over it. A refusal of a disabled control without the option says to add it.

`tapWords` and `dragWords` aim at words inside a paragraph, which another layer often handles (the text box link reader is a sibling of the paragraph, not its parent), so the rule cannot judge them: they only check that the point is inside the window ([#770](https://github.com/SunkenInTime/icarus/issues/770)).

The rule gets these cases wrong:
- **Refused, though a person could click it:** a label drawn on top of a sibling `InkWell` that is not its ancestor. Tap the `InkWell` by its key (`tapKey`).
- **Tapped, though a person cannot see it:** a control drawn at `Opacity(0)` still takes the press. A tap succeeding does not show that the control was visible; check what is on screen with a `shot` before relying on it.
- **Not seen as a handler:** a widget that takes presses in its own render object, such as a Material `Slider`, is not a listener, so a label it covers can be accepted. Check with a `shot`, or tap something with a handler of its own.

Steps that send no tap, such as presence checks, hovers and doors, do not use this rule ([#770](https://github.com/SunkenInTime/icarus/issues/770)).

## Windows

`build.ps1` and `run.ps1`; each one's header says how. Final checks happen here: Icarus ships to Windows, macOS and the web.

## Linux

Linux is for fast iteration on a box like t3os, where many agents can each verify on their own screen. It is not a platform Icarus ships to, so finish on Windows.

```sh
dart tool/drive/linux.dart build
dart tool/drive/linux.dart run --script tool/drive/scripts/right-click-local.json
dart tool/drive/linux.dart run --script tool/drive/scripts/shape-opacity-cloud.json \
  --companion tool/drive/scripts/shape-opacity-cloud-teammate.json \
  --account <email> --companion-account <other email>
```

`build` puts the build in `build/drive-linux` and talks to the dev deployment, or to a preview with `--convex <url>`. Production is refused. `run` starts its own Xvfb screen, so it needs no desktop and leaves every other screen alone. Each instance keeps its store, session, app data and log under `--out`, `drive-<run>` beside the build by default. Shots land there too, and so does the app's own error log (`home-<instance>/data/com.example.icarus/icarus_debug.log`), which holds startup errors that happen before the driver can log. `run` exits 0 when clean, 1 otherwise, and 2 when the script can't run here. `--help` lists every option.

Passwords come from `~/.agents/secrets/icarus/test-accounts.md`, or over `ssh windows` when that file is not on this machine. They go only into the app's environment.

`linux-stall-uploads.sh <exe dir> <new out dir> <label> <account>` runs `scripts/picture-upload-stalled.json` with picture uploads stalled for that run only: inside its own systemd scope, a connection whose TLS hello names `r2.cloudflarestorage.com` goes silent both ways once it has sent 64 KB, so a 197 KB picture never gets an answer while the 5 KB logo, Convex and every other process are untouched. The script signals when to lift it. It needs passwordless `sudo` for `iptables`, removes its rules on exit, and records the run's screen to `<label>.mp4` beside the out dir.

What doesn't run on Linux:

- The `clipboard` step puts a picture on the Windows clipboard through PowerShell. `run` refuses scripts that use it (`paste-on-canvas`, `paste-picture`, `paste-while-busy`).
- MP4 export needs `ffmpeg` on PATH. `run` refuses scripts that export MP4 when it's missing. Transparent MOV uses the app's own encoder.
- Growing the window to 2400x1350 (`spawn-barriers-all-maps`) crashes the Linux app with signal 11. Resizes up to 1600x900 work.
- A script that closes the window (`closeWindow`, as in `close-with-unsaved-local`) crashes in the Linux engine's teardown about half the time, after the save has finished: main at f0d6bb86 and #811 alike gave 2 SIGSEGV and 3 SIGABRT in 10 runs each. So on Linux such a script proves what was saved, not a clean exit; check the exit on Windows. The app closes before it writes `SUMMARY`, so `run` reports these runs as failed whatever their exit status; read the log of the run that reopens the strategy to see what was saved.
- The app draws system cursors instead of its custom drawing and rotation cursors, because the vendored `custom_mouse_cursor` has no Linux code. Shots don't include the cursor, so they look the same.

## How long a cloud open takes, by the back button

`{"cloudOpenTime": b, "from": a, "pages": p?, "items": n?, "runs": r?, "restAt": [x, y]}` (`scripts/cloud-open-time.json`) times opening cloud strategy b in place of a with the mouse back button, as a player does. With `items` it first gives b `p` pages of `n` items each (agents and text boxes) and waits for them to reach the server. Each of the r runs (20 by default) opens b, then a, then presses the back button at `restAt`, and logs `CLOUDOPEN run`: when the server read of b was done (b became the open strategy) and when its page was shown, both from the press. `CLOUDOPEN summary` gives the median and the worst of each.

`scripts/text-draft-switch-local.json` types into a text box and switches strategy with the quick switcher while it is still in the box, then comes back and logs the box's text.

At the end of every run `CANVAS` counts, besides the lines above, each time an edit reached the canvas while a strategy was opening (`an edit reaching the canvas during an open`), and names its caller. It should be zero in every script: while an open runs the editor takes no input.

## A rename while another strategy opens

`scripts/rename-while-another-opens.json` starts renaming cloud strategy A from the title, then opens strategy B in place through B's share link (`openShareLink`), which leaves the name field holding focus as a link does, then submits the field and checks both names in the library. `{"typeInFocused": text}` and `{"submitFocused": true}` type into and submit whichever text field holds focus, the way the keyboard does.

## How long an open takes to show

`{"openFirstFrame": "largest", "runs": 12}` (`scripts/open-first-frame-local.json`) times opening a local strategy the way a player does, from its tile in the library. It picks the strategy with the most items in the library it was started on (`"median"` picks the middle one, and a name picks that strategy), among those with a unique name and agents or abilities on their first page. Each run:
1. goes back to the library;
2. searches for the strategy;
3. presses its tile and lets go.

It then watches every frame until the editor is on top, showing that strategy's first page with all of its agents and abilities. From the pointer-up it logs when that frame was built and when it was rasterised. Raster times come from the engine's frame timings, matched by frame number. The summary gives the median and worst of each, with the strategy's size and the library store's mode. Start the run with `-HiveStore` on the library to measure and, if wanted, `-LibraryStore`.

With `"ahead": "median"` (`scripts/open-first-frame-abandoned.json`) each press also starts an open of the median strategy, so a store read the editor abandons is ahead of the timed one in the store's queue. Every `OPENFRAME run` line says what the mirror was doing when the run began; `scripts/open-first-frame-while-copying.json` opens once, as soon as the library shows the strategy (`"soon": true` skips the pause before the press), so on a large library started without a store the open happens while the mirror is still copying; launch it several times and keep the runs whose line says the mirror was waiting for the store.

`{"loadCopyCost": "largest", "runs": 51}` times the copy a page's load makes of its agents, abilities and utilities, on three pages: the page with the most of them in the strategy with the most, the library page with the most wall points, and a made-up page of 100 High Tides with 50-point walls. Each `COPY` line gives the median, fastest and slowest run and what the kept copies hold, so the work cannot be dropped.

`scripts/dont-save-local.json` turns autosave off, edits an agent's caption and weapon, an ability's wall and caption, a utility's caption, and moves the agent, then switches strategy and answers Don't save. It fails unless the strategy reopens exactly as saved (`{"rememberPage": tag}` and `{"expectPage": tag}` compare every item on the page), and unless a Duplicate made afterwards holds the saved items too.

`{"readBackCost": "largest", "runs": 21}` (`scripts/read-back-cost.json`) times, on the strategy with the most items, what the mirror spends converting it to rows, and converting it then checking that the rows read back equal to its Hive record, and logs both medians, the worst of each and the difference as a `READBACK` line.

`"budget": {"longestStepMs": x, "addedPerSaveMs": y}` on that step judges two of its numbers, each measured on the check alone, not on the whole save (the store's own write is not part of it):
- **Longest step:** the worse of the longest single steps it reports, cold and after one item changed (a freehand stroke moved when there is one). It is what a user feels, a frame the mirror holds.
- **Added per save:** the median the check adds once one item changed. It is the total work each save costs.

Each number gets a `READBACK <strategy> within budget: …` or `READBACK <strategy> over budget: <value> ms, target <x> ms, over by <d> ms` line, and the step fails if either is over.

`{"readBackFrames": pick, "longestStepMs": x?}` runs the same check with the real scheduler while a frame is asked for every frame, three times on one checker: cold, after one item changed as the editor changes it (a stroke's points, its box and the strategy's `lastEdited`), and with one item at -0.0, which reads back differently. Each run logs:
- how many breaks had no frame in them;
- the longest step between breaks;
- how many of the check's frames were timed, and the longest any of them waited after its vsync, matched by frame number.

It fails if no frame ran, if a break had no frame, if any frame of the check was not timed, if a step of the first two runs is over `longestStepMs`, or if the -0.0 item does not read back as its page reading back differently. The third run's longest step is logged beside the target but not judged: when a part differs, the verdict's words come from main's whole-page diagnostic, one step over the whole page, which only a page that reads back differently pays. A frame that is asked for waits behind at most the one step running when it was asked for. When nothing asks for a frame, the break does not wait for one.

`scripts/read-back-budget.json` runs both in mirror mode on the round library made by `test/library_store/read_mode_round_test.dart` (see below):

| Strategy | Longest step target | Windows release, worst of three rounds | Added per save target | Windows release, worst of three rounds |
| --- | --- | --- | --- | --- |
| largest | 4 ms | 2.8 ms | 8 ms | 5.0 ms |
| Dense strokes | 16 ms | 13.6 ms | 160 ms | 30.8 ms |
| Dense strokes, one item reading back differently (`readBackFrames`, not judged) | 16 ms | 234 ms | | |

Before the check ran in steps, main measured 9.9 ms and 128 ms for the longest step, and 3.8 ms and 110 ms added per save.

`{"pageTakeCost": 300, "changed": 1, "runs": 51}` times the cloud store taking a live page result, on SQLite in a temporary folder: a cloud strategy with one page of that many items (one in ten a 250-point freehand drawing, the shapes `tool/convex_cost/lib/content.mjs` writes), and a result in which `changed` of them changed. It logs a `TAKE` line with the median and worst of the longest main-isolate stretch during `record` and of the whole `record`, the median time the main isolate was busy, how many frames the app drew while it measured, and how busy the whole computer was just before and just after (all processes, from Windows' processor counter or Linux's `/proc/stat`), first as the store runs in a release build, then with every take also checked against one from scratch, as tests and driver builds run it. `"budget": {"longestStepMs": x, "recordMs": y}` judges the medians over all the step's takes (each take's longest stretch, and each take's whole `record`), never one take, with `within budget` and `over budget` lines like `READBACK`'s; an over line repeats how busy the computer was, so a failure on a busy computer can be read as one. The step fails if either median is over. `scripts/page-take-budget.json` judges one changed item on 300, and logs one on 60, ten on 300 and all 300:

| Page | Longest step target | Windows release, 2026-11-25 | Record target | Windows release, 2026-11-25 |
| --- | --- | --- | --- | --- |
| 1 of 300 items changed | 4 ms | 3.83 ms | 8 ms | 5.72 ms |

`scripts/read-mode-round.json` is a round to rerun before read mode is turned on. Make its library with `ICARUS_READ_ROUND_FIXTURE=<new folder> ICARUS_READ_ROUND_SOURCES=<Hive stores separated by ;> flutter test test/library_store/read_mode_round_test.dart`. That copies the stores, makes duplicate names unique against every name in them (a second `A` beside an existing `A (2)` becomes `A (3)`), and adds a strategy with an agent at x = -0.0, one with lineups saved interleaved and one page of dense strokes. Run the script on that library in read mode and in mirror mode. Then `ICARUS_READ_ROUND_BEFORE=<library> ICARUS_READ_ROUND_AFTER=<run>/store-main` with the same test compares Hive before and after, strategy by strategy, save time aside: only the strategy the script edits may differ. At the end of every mirror or read run, the store check lists a strategy the mirror recorded as reading back differently as `STORE expected`. It fails on a difference the mirror did not record, or on a strategy recorded as different that reads back equal.

## A change in one cloud strategy, then another opened

`{"mapThenOpen": B, "from": A, "runs": 50, "by": "back", "maps": [...], "restAt": [x, y]}` measures whether a map change made in cloud strategy A can be stored under B when B is opened at once (`scripts/map-then-open-cloud.json`). Each run:
1. opens B, then A, so the mouse's back button leads to B;
2. opens A's map picker and taps a map from `maps` that neither strategy has, each in the current map pool;
3. one frame later, opens B: with the back button pressed at `restAt` when `by` is `back`, as a player would, or with `openCloudStrategy` straight away, past the exit guard, when it is `open`;
4. reads both strategies from the server until one has the new map.

Each run logs where the change landed, how long after the tap its patch was queued and under which strategy, and how long after the tap B's open began. The summary counts the outcomes, and `expectTaken` fails the step unless B took the change that many times. With `shots`, the picker and the end of the first two runs are saved there, as is the screen when a tile can't be found.

## The cloud store in shadow

**Off until slice 3's PR 5.** The store now orders every result by its stamp, and the shadow's live results come from the editor's unstamped watches. `--cloud-store shadow` on Linux and `-CloudStore shadow` on Windows stop with exit 2 before starting anything, and the app refuses `--cloud-store=shadow` at launch. Use `--cloud-store send`. What follows describes the shadow as it ran before.

`--cloud-store shadow` on Linux, `-CloudStore shadow` on Windows, starts the app with the cloud store in shadow. It uses the same SQLite file as the library store, and either flag works without the other.

The shadow hears of every page the repository hands to the editor, the slices' fallback to the saved whole page included, after the editor has it (`ConvexStrategyRepository.tap`): as the server sent it, before the editor upgrades or merges anything, with the connection the app was on when the page was handed over. Nothing the shadow does can delay, change or stop what the editor gets. For the strategy the editor has open, it also watches the page list (`strategy:getPageList`), naming the account it serves (`accountSubject`), so the server refuses the watch rather than answer it as anyone else; settings are taken only from the page list, by the store's rule. The first result on a newer connection opens a session in the store before it is recorded. Nothing is sent from the store, no edit goes into it, and nothing on screen reads it. Its work runs one job at a time between frames, the way the library mirror does.

A shadow serves one account: the one signed in at the first sign-in it sees. Any later change of sign-in ends it for good. What it recorded before the change is still judged; nothing after it is recorded, and nothing new starts in that run. A page read through a share link is not taken.

The shadow proves the store records faithfully what it is given. It does not prove it is given everything the editor was given: that claim belongs to the step where the editor reads from the store, where it holds by construction. After each result it records, the store is compared with what the recorded results say it should hold, in order, by the store's own rules: the strategy row, the page list and its order, every page's row and settings, and the items and lineup groups of the page the result was for, with nothing extra allowed. Each recorded result ends compared equal, compared different, refused by the store or unreadable; a result received offline, on a connection that has since ended, or that the queue answered was from an ended session, is skipped. The driver logs this on `CLOUDSTORE` lines after every step.

At the last step the driver stops the shadow taking results and closes its page list watch, then waits for the shadow's queue to empty and the watch to close, at most 30 s from the last step. The run fails if any recorded result compared different, was refused or unreadable, if work was left, or if the shadow stopped. Then the store is closed, opened again from disk and compared whole against the same expectation: every strategy's row, page list and settings, and the contents of every page it recorded; a strategy missing from the file, anything extra in it, or nothing to compare fails. A counts line, printed and never judged, says how many pages were handed to the editor, how many the shadow recorded, and how many were skipped or not taken and why. With the flag off, nothing of the shadow is created.

The driver steps that go with it:

- `{"openStoredCloudStrategy": true}` opens the one cloud strategy the store holds, so a run started on another run's store with `--hive-store` (`scripts/cloud-store-shadow-restart-after.json`) opens the strategy that run left behind.
- `{"expectPageListRefusedNaming": subject}` reads the open strategy's page list naming account `subject` and fails unless the server refuses it with `ACCOUNT_MISMATCH`; run it signed in as another account to see a read that names someone else refused.
- `{"expectBatchRefusedNaming": subject, "readsAccountMismatch": true}` sends the open strategy an empty `applyBatch` naming account `subject` and fails unless the server refuses it: with `ACCOUNT_MISMATCH` when `readsAccountMismatch` is true, with `FORBIDDEN`, as shipped builds get it, when false. `scripts/account-mismatch.json` runs both and the page list refusal, signed in as anyone but the account it names (jules@'s).
- `{"sendUncheckedDelete": id, "basisAgeMs": n, "expectRefused": b}` asks the server for its time with an empty `applyBatch` that sets `sendsLiveBasis`, then sends an unchecked delete of the open page's item `id` (`lastWriterWins: true`) with a live basis `n` ms before that time. It fails unless the server refuses it with `UNCHECKED_OUTSIDE_WINDOW` when `expectRefused` is true, or applies it when false. Both sends use the same op id, so a refused one must leave nothing behind for the next. `scripts/unchecked-window.json` sends one 30,001 ms old (refused, the agent stays), then a fresh one (applied, the agent goes).
- `{"expectStoredPayloadVersion": id, "version": n}` fails unless the store holds item `id` at payload version `n`, as the server sent it; `scripts/cloud-store-shadow-old-payload.json` sends an item at an older version the way an older build writes it.

`scripts/cloud-store-shadow-offline.json` waits for `cut` and `restored` signals, which `linux-cloud-store-offline.sh <exe dir> <new out dir> <account>` writes: it runs the script inside its own systemd scope, drops that scope's incoming traffic with an nftables rule once the script signals `ready`, and lifts it once the script has edited offline. It needs passwordless `sudo` for `nft`, removes its rule on exit, and stops its run if it exits early. Linux only.

`linux-cloud-store-late.sh <exe dir> <new out dir> <account> <script> [<companion script> <companion account>]` cuts the main instance off both ways, so a call it sends is held by the network instead of answered, and arrives late once the network is back (the case the server's window refuses, issue #714). It runs the scripts in send mode with `--main-scope`, so the main instance has a systemd scope of its own and the companion stays online. When the main script signals `ready` it drops everything that scope sends or receives, and signals `cut`; when the script signals `restore` it lifts the rule and signals `restored`. A script whose last step is `killNow` ends there on purpose, before any `restore`: the wrapper exits 0 when the log shows the kill and no step failed. It needs passwordless `sudo` for `nft` and removes its rules on exit. Linux only.

`getPageList` has to be on the deployment the build talks to.

### Sending from the store

`--cloud-store send` (`-CloudStore send`) runs a sender for the store's queue (`lib/library_store/cloud_sender.dart`) and no shadow. The sender is one loop that does one thing at a time: it waits for a change, takes one snapshot of the inputs (the account signed in, the connection, the sign-in and sign-out counts), and does one step for the strategy served least recently: open its session, close an attempt no call answers, send (claim, check the snapshot still holds, call `ops:applyBatch` as the strategy's owner opted in to `ACCOUNT_MISMATCH`, record the answer), or make one read of its own. Every result the store records comes from those reads: `strategy:getPageList` or `page:getSnapshot`, named for the strategy's account. The sender reads a strategy's page list and every page when the editor opens a strategy the store does not hold (which pages still need their first read comes from the store, so a restart resumes them; reopening a strategy the store holds reads nothing more), the page list or page each need of the queue asks for, the page list after `FORBIDDEN` (its role lifts edit access lost), and, once a strategy has been quiet for 30 s, each page with landed work, not again within five minutes. A need the queue still raises after its read was recorded is read again after 2 s, then 4 s; after three such rounds the strategy shows that it could not be resolved (`could not resolve` in the sync lines) and its reads wait ten minutes, or until the queue changes. A read refused as `FORBIDDEN` is shown beside the sync state (`read hold`) and tried again after ten minutes; a lost or unreadable read is tried again after 2 s, doubling to ten minutes. A page list that says the account can only view waits ten minutes before the same loss of edit access is read again; a new loss is read at once. What the sender remembers about a strategy's reads (rounds, waits, failures, the `FORBIDDEN` fact, the viewer's answer, when each page was last read to retire landed work) belongs to one account, connection and sign-out count: when any of them changes, all of it is forgotten and the strategy starts clean. A request to read a strategy into the store belongs to the sign-in it was made under and is dropped when that sign-in ends; the editor's open strategy is asked for again under each new one. A hold lets the step in hand finish, its answer included, and starts nothing new. At the end of a run the driver reads every cloud strategy of the signed-in account itself, named, and compares the store with what the server holds twice: as the run left it, and after the store is closed and reopened. Nothing reads the store again between the two, so both show what the sender itself recorded. The run fails if a strategy the script named with `storeExpect` gets no verdict, if any comparison differs other than a row the script named with `storeMayLag` held at an older revision, if any result of the server's gets no verdict, or if work is left in a queue.

Its steps:

- `{"storeExpect": true}` waits until the store holds the open strategy (60 s, or `"within": seconds`) and names it as one the end-of-run comparisons must judge; `{"storeExpect": "held"}` names the one cloud strategy the store holds, for a run that opens no editor.
- `{"storeAdd": id, "kind": "agent", "at": [x, y]}` commits an add of an agent (or `"kind": "smoke"`, a Brimstone smoke) at map position `(x, y)` to the first page of the store's one cloud strategy, as the account signed in. In send mode the editor still writes to the server itself, and the sender reads nothing the queue does not ask for, so an item placed in the editor never reaches the store; a script that moves items through the store makes them this way.
- `{"storeAddPage": true}` commits an add of a page to the store's one cloud strategy, as the account signed in, with no editor involved.
- `{"storeMove": id, "by": [dx, dy]}` commits a whole-row move of element `id` to the store, at the revision the store holds, as the account signed in; with `"startingWith": true`, of the first element whose id starts with `id`.
- `{"storeMove": id, "by": [dx, dy], "merge": true}` commits the same move as a field merge of `position`, which the server applies over a teammate's change to the row.
- `{"storeMayLag": "<item id>", "why": "..."}` says the store may hold that item at an older revision than the server at the end of the run, and why (a teammate's change, or an edit made in the editor, that nothing in the queue asks for). It excuses only that difference; anything else in the strategy still fails.
- `{"addPage": true}` adds a page to the open strategy, as the pages bar's add button does.
- `{"storeDeletePage": n}` commits a delete of the store's one cloud strategy's page `n` (counting from 0) as the account signed in, with no editor open.
- `{"setMemberRole": "viewer"}` sets the role of the open strategy's one member (a teammate who joined by link) to `viewer` or `editor`.
- `{"breakConvexSignIn": true}` gives the Convex client a token the server refuses, the way an expired sign-in the app cannot refresh looks; `{"restoreConvexSignIn": true}` has the app set its Convex sign-in up again.
- `{"holdSender": true}` and `{"releaseSender": true}` hold sending and let it go again; answers already received are still written while it is held.
- `{"waitStoreSent": seconds}` waits until every queue is empty and no landed work waits for a result; with `"landed": "may wait"` landed work may still wait.
- `{"expectStoreNeedsYou": true}` logs every entry that needs the user, with the queue's reason, and fails if there is none; `{"storeUseCloud": "<item id>"}` takes the cloud's version of each entry that needs the user in the strategy holding that item, as the signed-in account; the store refuses it when that account does not own the strategy.
- `{"storeDelete": id}` commits a delete of element `id` as the account signed in; the queue decides whether it goes unchecked.
- `{"storeSetField": id, "field": name, "to": value}` commits a field merge of one data field of element `id`.
- `{"waitStoreRefusedLate": seconds}` waits until the queue records a batch the server refused as arriving too late for its basis.
- `{"waitStoreHeld": seconds}` waits until the store's one cloud strategy is held for lost edit access with work unsent, and the sender's page-list read for that loss said the account can only view it; it fails if that does not happen in time.
- `{"storeSyncState": true}` logs each cloud strategy's sync state for the account signed in, whose work it is, and the sender's state.
- `{"storeDiscardUnreadable": true}` discards the unreadable queue of the one cloud strategy in the store, as the user would after acknowledging it, and fails if the store does not take the discard. `cloud-store-discard-after.json` runs it over a store whose queue cannot be read, then waits for the strategy to be read again.
- `{"storeSessionOpenings": true}` logs each session the sender's writes opened in the store, and what opened it: the app start, an account change, the reconnect event, or a result's stamp from a later connection. With `"byStamp": "expected"` the step fails unless at least one was opened by a stamp. `cloud-store-send-offline.json` uses it after a page delete made just after the cut, whose reads cross it.
- `{"killNow": true}` ends the app at once, the way a crash does.
- `{"signOut": true}` signs out through the app's own confirmation; `{"signIn": "second"}` signs in to `--second-account` (Linux).

The scripts: `cloud-store-send.json` (ops sent and the store equal to the server), `cloud-store-send-owner.json` with `cloud-store-send-teammate.json` (a teammate's edit first, so the owner's op needs the user), `cloud-store-send-offline.json` through `linux-cloud-store-offline.sh <exe dir> <out> <account> <script> send` (an answer lost, the same op id resent and answered as already applied), `cloud-store-send-restart-before.json` then `cloud-store-send-restart-after.json` with `--hive-store` (unsent work sent once after a restart), `cloud-store-send-account.json` with `--second-account` (nothing sent for another account, sent once the owner is back), `cloud-store-send-closed-before.json` then `cloud-store-send-closed-after.json` through `linux-cloud-store-offline.sh <exe dir> <out> <account> <script> send <store>` (saved work sent with no editor open, then a move made offline sent once the connection is back), `cloud-store-send-expired.json` (an expired sign-in during a send: no call storm, sent once signed in again), `cloud-store-send-page-delete-before.json` then `cloud-store-send-page-delete-after.json` with `--hive-store` (a page delete made with no editor open: the page list and the page read, then sent), `cloud-store-send-merge-owner.json` with `cloud-store-send-teammate.json` (a field merge lands over a teammate's move at a revision the queue did not predict, so the next whole-row move reads the page first), `cloud-store-send-access-owner.json` with `cloud-store-send-access-teammate.json` (the owner makes the teammate a viewer: the teammate's send is refused, its page-list read keeps it held; made an editor again, the next read on a new connection lifts it and the move is sent; then the same again within ten minutes, where the second loss is read at once, not held by the first viewer's wait), `cloud-store-send-refresh.json` (the Convex sign-in set up again for the same account mid-session, and the sender's reads still recorded after it), and these for the server's window for unchecked sends:

- `cloud-store-late-owner.json` with `cloud-store-late-teammate.json` through `linux-cloud-store-late.sh`: the #714 case. The owner deletes an item as the network is cut, unchecked on a fresh server time; the teammate moves it; the network comes back. The late call is refused by the server, the checked resend is rejected, and the owner is asked and takes the cloud's version. The teammate's move is still there.
- `cloud-store-late-alone.json` through `linux-cloud-store-late.sh`: a field edit sent into a cut network and held past the window with no teammate. The late call is refused, the checked resend lands, once.
- `cloud-store-late-refused.json` through `linux-cloud-store-late.sh`: the network comes back while the sender still waits for its call, so the sender sees the late refusal itself. A same-field edit made while sending is held goes out checked, as does the resend. The cut comes 15 s after the last answer, so the edit still goes out unchecked (the sender sends unchecked only on a server time under 20 s old), and the network comes back 16 s after the edit's 3 s pause. By then the server time is about 35 s old, so the call is late however it gets through: on its own retry within a second of the network coming back, or on the TCP retransmit at about 25 s after the send, well inside the call's 45 s limit.
- `cloud-store-late-restart-before.json` through `linux-cloud-store-late.sh`, then `cloud-store-late-restart-after.json` with `--hive-store`: an unchecked edit in flight when the app is killed is sent checked after the restart.
- `cloud-store-fields-owner.json` with `cloud-store-fields-teammate.json`: two people edit different fields of one item at once; both go unchecked and merge, with no prompt.
- `cloud-store-race-owner.json` with `cloud-store-race-teammate.json`: both move the same item at once while active; both go unchecked and converge on the last arrival, with no prompt.
- `cloud-store-race-quiet-owner.json` with `cloud-store-race-quiet-teammate.json`: the same after 30 s of quiet; both go checked, and one of them is asked.

## The library store in shadow

`--library-store shadow` on Linux, `-LibraryStore shadow` on Windows, starts the app with the library store switched to shadow: as it starts, it copies every local strategy and folder from Hive into a SQLite store beside the Hive boxes (`library_store/library.sqlite`), reads every strategy back out and compares it with Hive. Nothing reads the store yet. `--hive-store DIR` (`-HiveStore`) starts the main instance on a copy of `DIR`, which is never opened itself, so a real library can be checked without touching it.

```sh
dart tool/drive/linux.dart run --script tool/drive/scripts/library-store-shadow.json \
  --library-store shadow --hive-store ~/Code/<scratch>/store
```

Every run logs `FIRSTFRAME <ms> ms store=<off|shadow|mirror>`, the time from the start of `main` to the first frame on screen; `scripts/first-frame.json` does nothing else. The steps:

- `{"libraryStore": "shadow", "seconds": n?, "expect": {...}?}` waits up to n seconds (600 by default) for the copy and the comparison, logs them as `STORE` lines, and fails unless the store opened, the copy finished with nothing left out, every strategy and folder reads back the same as Hive, and neither library box (`strategy_box.hive`, `folder_box.hive`) changed while it ran. Other boxes the app writes on its own in that time are listed, not failed; `test/library_store/shadow_copy_test.dart` hashes every Hive file around the copy alone. `expect` can name counts that must match: `copied`, `unchanged`, `tookHiveVersion`, `removedWithHive`.
- With `"hidden": true`, the step first tells the app it is hidden, as the system does when its window is minimized, so no frame is drawn while it waits, then shows it again. `scripts/library-store-shadow-hidden.json` uses it: the copy and the check must finish without a frame.
- `{"checkLibraryStore": 1}` reads every strategy back again and fails on any difference.

With `--library-store mirror` (`-LibraryStore mirror`) the app does the same copy at start, and after it every save of a local strategy or folder that Hive accepts is followed by the matching store write, through one queue. At the end of every script the driver waits for that queue to drain, checks the store against Hive, logs the `STORE` lines and fails unless it is exact; `{"holdLibraryStore": true}` stops the queue, so a run can end with saves Hive holds and the store does not (`scripts/library-store-mirror-hold.json`), for the next start to bring up to date.

With `--library-store read` (`-LibraryStore read`) the app mirrors as above, and the library list and folders are drawn from the store wherever the store is known to equal Hive. Until the start-up copy has finished, every strategy and folder is drawn from Hive. After it, an id is drawn from Hive from the moment a save touches it until the mirror has written it, and whenever the store does not hold it; every other id is drawn from the store's summaries, in Hive's order. The list redraws on the same Hive box changes as it does in every other mode, so nothing on screen waits for the store. A strategy the store does not hold (the converter refuses it, or the store cannot read it) carries a "Not in the store" mark on its tile. So does a record the store cannot name by its id: one whose box key is not text, is not its id, or whose id another record in the box also carries. The copy and the mirror leave such records out of the store, the list draws them from Hive by their box key, and the end-of-run check counts them as `kept on Hive` and logs each with `STORE kept on Hive` and the reason. If the mirror is held or stops, the list is drawn from Hive. In read mode the tiles' dates are the milliseconds Hive and the store both store, so a strategy does not move between sorts when it moves between the two. In mirror and read runs the driver logs what is on screen right after each step, then again (only if it changed) once the mirror has written what is pending, so a state the list passes through on its way shows in the log; a step after which the mirror has not drained within 30 s fails. Each time the list's source changes the driver logs `LISTING <step> drawn from Hive` or `the store`, and at the end of a read run it fails unless the list is drawn from the store (or the mirror was held).

Read mode also opens a local strategy's pages from the store (`lib/library_store/store_page_reads.dart`). Each page load, an open or a page switch, comes wholly from the store (its page, the pages bar's list and the theme) or wholly from Hive, and the driver logs it as `STORE page open|pageSwitch <strategy> page <page>` with its outcome and the time the read took. The outcome is recorded when the editor applies the page: `from the store`, `from Hive: <reason>`, `never shown` when a newer open or load took its place first, `failed: <error>` when the open or switch threw (an open of a strategy Hive no longer holds included), or `no page to show` for a strategy with no pages. Every open records exactly one of these, from the moment it starts, and so does every switch that reads a page. A load that falls back to Hive draws Hive as it is when the store answers. Whichever source answered, if a Hive write to the strategy began after the read, the page is drawn from Hive as it is when it is applied. A load comes from the store only when the open migrated nothing, the mirror is following, the strategy is not one the mirror says may differ from Hive, the store keeps it here, no two pages share a position, the store holds the page asked for, every row read is one this build can show, and no Hive write to it began during the read. A page switch first writes the page it leaves to Hive, so a switch almost always comes from Hive with `may differ`. `{"logPageReads": tag, "expect": {key: n}?}` logs the loads since the last one and the counts by key (`openFromStore`, `openFromHive`, `openGaveWay`, `openNoPage`, `openFailed`, the same for `switch`, and each reason's name, such as `mayDiffer`), failing on any count that differs; outside read mode it logs that pages come from Hive and fails only if counts were expected. Every read run ends with `STORE page loads in the run`.

In read runs every `LIBRARY` log is followed by a `GRID` line counting the local strategy tiles and local folder cards on screen (not cloud cards or the folder dialog's preview) by where the row each was built from came from, the store or Hive, then one `GRID ... from Hive` line naming each one built from Hive while the list is drawn from the store. These count the rows the mounted grid holds, not what the list would answer. Between `{"framesStart": 1}` and `{"framesLog": tag}`, the driver also finds the frame drawn after each notice the library list sends and `framesLog` logs that frame's build and raster times as `FRAMES tag after a list notice`. The frame is the one whose vsync started within 25 ms before the frame time Flutter was given, which is one refresh later; a frame with no timing logs `not timed`. In a read run a strategy's catch-up sends one notice more than mirror mode does, so that frame is the cost of the redraw.

- `{"libraryFromStore": label, "seconds": n?, "expect": {...}?}` waits up to n seconds (600 by default) for the list to be drawn from the store, and logs how long after launch that happened, how many summaries the store rebuilt as it opened, and every strategy and folder still listed from Hive, with why. `expect` can name counts that must match: `rebuiltAtOpen`, `fromHive`, `foldersFromHive`. Then, within 2 s, the grid on screen must hold at least one store row and no Hive rows but those marked "Not in the store", or the step fails.
- `{"gridRowFromStore": name, "since": mark?, "seconds": n?}` waits up to n seconds (10 by default) for the one tile or folder card named name on screen to be built from a store row, and logs the milliseconds since mark.
- `{"holdListOnHive": true}` keeps the list on Hive after the store is ready, until `{"letListGo": true}`, so a script can set the screen up (scrolled, a menu open) and log it just before the list moves. As a script's first step it holds from launch, before the store can be ready.
- `{"expectStoreRefuses": [ids]}` names strategies the script expects the store not to hold; the end-of-run check passes when they are the only difference.
- `{"watchLibraryText": t, "since": mark, "gone": b?, "seconds": n?}` watches, behind the next steps, for text t to reach (or with `gone`, to leave) the library on screen, and logs `TIMED` with the milliseconds since mark. It waits for the next action marked with that name, not one marked earlier, allows n seconds (10 by default) from that action, and fails if the text is already where it is watched for when the watch starts. `tapText`, `tapKey`, `dragAt` and `key` take `"mark": name`, which starts that clock as the button is let go or the key pressed.

`scripts/library-not-in-store.json` runs on the fixture `test/library_store/drive_fixtures_test.dart` writes with `ICARUS_NOT_IN_STORE_FIXTURE=<new folder>`: a strategy from a newer build, which the converter refuses, and one whose row in the store is damaged. `ICARUS_SMALL_LIBRARY_FIXTURE=<new folder>` writes the same library without those two, for `scripts/library-move-then-look.json`. `ICARUS_KEPT_ON_HIVE_FIXTURE=<new folder>` writes a library with records the store cannot name by id (two folders sharing an id, one of them and a strategy under integer keys, a folder under a key that is not its id) beside a folder and a strategy it can, for `scripts/library-kept-on-hive.json`, which checks they are drawn from Hive with the mark and renames the folder under the integer key from its card. `ICARUS_AGE_STORE=<a scratch copy's library.sqlite>` rewrites every summary in that store as the build before this summary version wrote it, for `scripts/library-switch-to-store.json`, which then shows the list moving from Hive to the store; `scripts/library-second-start.json`, started on the store that run left, checks that nothing is rebuilt the next time. Those two and `scripts/library-rename-then-look.json` name strategies of the synthetic 700-strategy library.

Every run logs `FRAMES whole run`: the frames drawn, the worst one from the start of its build to the end of its raster, how many took over 50 ms, and the longest the main isolate was busy, measured passively from the start of the script to its end.

`test/library_store/drive_runs_test.dart` compares two runs' saved libraries (`ICARUS_COMPARE_RUNS=a:b;c:d`, run ids, generated ids and times set aside) and checks the store a run left against its Hive library without copying first (`ICARUS_CHECK_RUNS=a;b`).

At the end of a run the driver closes the store and logs `STORE closed`.

`scripts/open-race-leave-local.json` races a strategy switch against a page click, the way a fast player can. Its step `{"raceLeave": b, "from": a, "page": p, "switcherAt": [x, y], "runs": n?, "unusedPictures": k?, "expectEmptied": m?}` does this n times (50 by default):
1. Opens strategy a.
2. Leaves k unused picture files (20 by default) in b's folder, so the open has cleanup to do.
3. Opens the quick switcher at `switcherAt` and clicks b.
4. One frame later, once the switcher has closed, clicks a's page p in the pages bar.

With `"second": "undo"` the second action is Ctrl+Z instead of the page click: before each run it moves one of a's agents and saves, so there is an edit to undo. `RACE run` then also says whether the undo was taken while the open ran (a's agents changed on screen before b became the open strategy) and whether b ended marked unsaved; `RACE summary` counts both, and how many runs pressed Ctrl+Z while the open ran (before b became the open strategy). `expectTaken` fails the step unless the count of undos taken matches, and also when no run pressed during an open, since then nothing was tested. `scripts/open-race-undo-local.json` runs it.

It times the open from inside the app, with provider listeners rather than polling. For each run it logs `RACE run`: whether a's first page was saved without its agents, when the canvas was cleared, when the second click landed, and when b became the open strategy. The window is the time between the clear and that moment. Then it puts a back as it was. `RACE summary` gives the count and the window's median and worst. With `expectEmptied` the step fails unless the count matches.

`--kill-after-seconds S` (Linux only) kills the main instance with SIGKILL S seconds after it starts, as a crash would. Start the next run with `--hive-store <that run's out>/store-main` and `scripts/library-store-shadow.json` to see the copy pick up where it stopped.

## Editor actions as ops

With `--library-store ops` (`-LibraryStore ops`) the app mirrors as above, and also turns every editor action on a local strategy into the ops that would change its rows, committing each action's ops to the store in one `commitAll`, in the mirror's queue. Hive stays the truth and nothing on screen reads these rows. Only this flag creates the follower that does this; without it the editor's hooks are null and do nothing.

The checker is a gap finder. A finding is evidence of a gap. A unit with no finding is evidence of nothing, and its counts are a list of gaps found, not a coverage figure: nothing may use them as a gate.

The follower works in units. A unit is everything that happened in one turn of the event loop: the actions the editor reported, and any change to the canvas without one. While a pointer is down, or a text box holds a draft, turns join one unit until the pointer is released or the draft is gone. At the end of a unit the follower copies what the canvas holds (the page on screen, the strategy's name, map and theme, and the other pages as Hive holds them) and hands the journal the copy and the actions. The journal builds and commits each action's ops, replays the actions onto the previous copy, each from its own before and after, and looks for three kinds of finding:

- **Changed without an action.** The new copy differs from the replay: the canvas changed and no action declared it.
- **The action's before did not match the canvas.** An action's before for a field differs from what the previous copy held. The action may still have declared and written the right final value.
- **Ops wrong.** The store, read back, differs from the replay.

A unit is counted when it opens. Each one ends in exactly one disposition: with a finding (one or more of the three), no finding, no change, not judged with its reason (a follower fault, a page loading, the strategy opening or closing, a refused commit, a store that could not be read), or discarded with its reason (actions inside a page switch, actions as the strategy changed, actions before the mirror was following, a unit still open at the end, the mirror stopping). After the checks the store is put right from the canvas if it differs, so one miss does not spoil the next unit. The counts must add up: units opened equals the units given a disposition plus the units still open. The `actionOps` step fails when they don't, and so does the end of the run, where nothing may be left open.

A unit with no finding does not establish that nothing was missed. In particular:

- the store is compared once, at the end of the unit, so an add and its undo inside one held unit leave nothing to find even with both ops dropped;
- `before` is not checked for every field (link details and landing visibility are skipped), so a later edit can hide an undeclared one;
- only the page on screen is compared after an ordinary unit, so an op that writes to another page is not found;
- the text draft, a drawing in progress and lineup previews are not part of the canvas copy;
- replay and the builders treat a landing's visibility toggles as one field, where the editor merges them one by one.

The strategy is taken up when it opens, once its page is drawn: the store gets the canvas, and how the canvas differed from Hive at that moment is counted. A page switch puts the store right if the store is behind. Closing releases the strategy and puts Hive's value back, so a "Don't save" leaves the store as Hive holds it. A Hive save of a taken-up strategy never moves the store; after the turn it was made in, it is compared with the store and reported as a second table. While a strategy is taken up, read mode treats it as not known equal and draws it from Hive. A fault in the follower never reaches the edit: it is counted, the follower stops taking actions, and its units are not judged until the strategy is opened again.

At the end of the run the driver saves the open local strategy, closes out any unit still open, releases the strategy and logs the `OPS run` lines: units by disposition, findings by kind, the same per action kind, every finding with the fields it names, commits and refusals, follower faults, how the canvas differed from Hive at open, the Hive save report, and the time the copy, the replay and the comparison took, grouped by how many items the page held.

- `{"actionOps": label, "expect": {...}?, "expectKinds": {...}?}` waits for the queue to drain and logs the `OPS` lines so far. It fails if the units do not add up. `expect` can name counts that must match: `unitsOpened`, `unitsWithFindings`, `noFinding`, `changedWithoutAction`, `beforeNotOnCanvas`, `opsWrong`, `notJudged`, `discarded`, `commitsRefused`, `followerFaults`, `hiveSavesDifferent`. `expectKinds` maps an action kind, as the `OPS` lines name it, to the number of units of that kind the run must have opened so far.
- `{"fillPage": n}` adds agents and texts to the page on screen in one transaction until it holds n items. `scripts/ops-cost-24-local.json`, `ops-cost-240-local.json` and `ops-cost-960-local.json` time the checker on pages of those sizes.
- `{"slowStoreCommits": ms}` makes every store commit wait that long first (driver builds only), to show that nothing in the editor waits for one. `scripts/ops-strokes-with-slow-commits.json` draws three strokes with commits at 200 ms.
- `{"path": [...], "firstFrame": label, "opStillPending": true?}` logs, in the first frame after the release, the drawings on screen and whether the commit of the stroke's own action has returned; with `opStillPending` the step fails unless it had not.

## Keeping the two in step

`run.ps1` and `linux.dart` are two launchers for the same driver. The driver decides pass or fail and writes the `SUMMARY` line; the launchers only set it up and read the log. `test/drive_linux_runner_test.dart` fails when the driver reads an `ICARUS_DRIVE_*` variable one launcher doesn't set, when Linux refuses a step the driver no longer has, or when either build stops refusing production. A change to what an instance gets goes into both launchers in the same commit.
