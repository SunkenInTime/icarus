Run one chaos gauntlet before choosing Icarus's Dart client

Dartvex is the leading candidate because it targets the typed Dart API and build simplicity Icarus wants. convex_flutter still has the stronger native sync lineage and already runs in the app. Put both behind the same Icarus transport, run 50 seeded trials and 50,000 operations per client, then choose from evidence. Do not build a custom generator or migrate the app before this gate closes.

Recommended decision: test Dartvex first and adopt it if it preserves every operation, catches a contract break at compile time, and stays within 20% of convex_flutter on profile-run latency and memory. Otherwise keep convex_flutter and return to the fallback generator plan.

Confidence is medium. Repository structure, package source, public issue state, and current Icarus call paths were inspected on 2026-08-25 and 2026-08-26. Neither client has run this Icarus workload yet. Raw throughput is not the first gate because a fast client that loses one library operation is disqualified.

This document does not replace Convex, redesign page-scoped sync, change Hive models, or change the .ica format. It selects the Dart client and contract tooling used below those stable product rules.

Transport contract

  • Query, mutation, action, and subscribed query operations.
  • Connection state, reconnect, subscription cancellation, and client disposal.
  • Supabase access-token delivery, forced refresh, auth-state confirmation, and sign-out.
  • Structured errors that omit tokens, signed URLs, and strategy payloads.

Do not let either adapter own the outbox, operation IDs, revision rules, payload versions, Hive storage, or .ica conversion. Those are common Icarus logic. A package cannot win by silently changing them.

Use a stable fixture such as folders:listForParent. Generate the Dart API, compile one correct caller, then rename one argument and one result field in a temporary Convex function-spec fixture. Regenerate and require the old caller to fail analysis at the affected fields.

Then run the cloud round-trip chaos test

Use base-test-v43.ica as the initial library artifact. Clients A and B use two disposable Supabase users with access to the same strategy. A clean client C performs final verification with no local cache.

Workload per seed

  1. Import the fixture and wait until the server snapshot matches its canonical form.
  2. Subscribe A and B to the strategy shell and active page.
  3. Run 1,000 deterministic operations across page descriptors, page content, elements, lineups, and page order.
  4. Create two same-revision edits on the same entity. One must land and one must become a visible conflict.
  5. Fetch the full snapshot through C, export it, canonicalize it, and compare it with the reference reducer's expected state.

Fault schedule

  • Dispose and recreate the client at seeded intervals, including while a mutation result is unresolved.
  • Hold the connection offline for 2 to 10 seconds while new edits enter the common test outbox.
  • Cancel and recreate the active-page subscription while the other client continues editing.
  • Present one rejected or expired access token, refresh the Supabase session, and require Convex authentication to recover without losing queued work.
  • Background and resume the Flutter app while subscriptions and pending operations exist.

The current app refreshes a Supabase session when its token expires within one minute. Preserve that behavior and test it through each adapter. Use publishable client credentials and disposable test accounts. Never place a Supabase service-role key in Flutter, the test log, a fixture, or committed configuration.

Keep the current outbox limitation out of the SDK score

The current outbox is memory-only. A full process restart can therefore lose common Icarus state before either SDK sees it. For this comparison, persist the seeded operation ledger in the test runner and replay the same clientId and opId after recreating the client. Test the real durable app outbox separately under the page-scoped sync plan.

Source: Icarus library and sync-status guarantees in AGENTS.md. The 20% performance margin is this evaluation's declared decision threshold, not a measured result.

Any lost operation, duplicate effect, silent conflict, stale subscription after reconnect, false synced state, or final canonical mismatch is one correctness fault. One fault loses the gate. Do not average it away.

If both adapters fail the same seed at the same common Icarus boundary, neither wins. Fix the shared implementation or the test, then rerun. If both pass, Dartvex wins only when its codegen also closes the compile-time contract.

Deliver evidence, not a package swap

  • One injected Icarus client interface and two adapters.
  • One deterministic contract-drift test and one real deployment chaos test.
  • Machine-readable results with seed, adapter, SDK version, commit, platform, fault schedule, correctness counters, p95 latency, reconnect time, CPU, and peak memory.
  • A short result document naming the winner and linking every failing seed or profile run.
  • No broad migration, custom generator, production deployment change, or removal of convex_flutter in the comparison PR.

Run profile measurements in alternating adapter order to reduce backend and network drift. Use at least 10 paired runs after the 50 correctness seeds. Report the median of each adapter's paired p95 values and peak memory. Do not claim a speed win from debug builds.

Stop conditions

  • The selected Convex deployment is production or contains public user data.
  • The comparison requires weakening a server validator or changing an Icarus payload solely to satisfy one SDK.
  • The refreshed cloud branch has incompatible client-abstraction or codegen work already in progress.
  • Fault injection cannot give both adapters the same operation and timing semantics.
  • A destructive development-deployment reset is proposed without verifying that only team data exists.
  • Unrelated dirty changes overlap auth, repository, queue, sync-state, or generated files.
