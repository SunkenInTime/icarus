# ADR 0011: Every cloud answer can say which state of the client it comes from

**Status:** Accepted (2026-11-25)
**Feature:** The app's Convex transport (`lib/collab/transport/`, `lib/collab/src/convex_client_*.dart`, the generated `StampedConvexQuery`), on the vendored clients' timed calls (`third_party/convex_rs`, `third_party/convex_flutter`, their `ICARUS_PATCH.md`)

## Context

The library store is to take the editor's live results and its own one-shot reads and batch answers, in whatever order they reach Dart. A live update can arrive after a newer read; two snapshots can share a server time; a reconnect can start the server's time earlier than before. Nothing the app received said which of two answers was newer.

## Decision

The stamped calls (`StampedConvexTransport`, `StampedConvexQuery.fetch`, `watch` and `watchTogether`, `mutationStamped`) answer with a `ResultStamp`. They work only on a client built with `ConvexConfig.countsTransitions`, and fail loudly on any other. The released app does not set it; the store turns it on where it uses stamps, which is known when the clients are built at startup. The ordinary calls are unchanged and never reach the stamped path. A stamp holds:

- **client**: which client in this run of the app gave the answer. Stamps of two clients are never compared.
- **snapshot**: how many server transitions that client had applied when the answer was taken. For one client, a higher snapshot is a newer state, and two answers of one query with the same snapshot are the same answer. On native it counts transitions in the Rust client from the client's start. On web it counts the JS client's transition dispatches from the moment the client is built, before it holds any query; the dispatches include one the JS client makes locally when a mutation fails. Both only go up.
- **connection**: the connection generation the client was on when it applied the state the answer comes from. A higher number is a later connection, and numbers can be skipped. On native it goes up each time the client starts again on a new socket, a failed dial included. On web it is the JS client's `connectionCount` at the transition that carried the answer, which goes up each time a socket opens. A value the client still holds from an earlier connection keeps that connection's number, even when it is handed to a listener after the socket has opened again. `connectionGeneration()` gives the generation the client is on now; an answer stamped lower comes from an earlier connection.
- **serverTime**: the snapshot's server time in nanoseconds. It is absent before the client has applied any server state: an answer given before the first transition (a failed mutation, an action, an empty group), and on web the JS client's local dispatches before its first server transition, which carry the initial time zero. A server transition never ends at zero, because its time is the database's, in nanoseconds since 1970, so zero always means "none". The time does not order answers on its own: two snapshots can share it, and a new connection can start at an earlier time, on both platforms. On web it is a JavaScript number, so above 2^53 it is rounded to the nearest representable value, whose spacing grows with the magnitude (256 ns for today's times). The rounding never turns a time that is at or after another into one before it, but it can make a time up to one spacing before another look equal to it, so "at or after" can hold on web for a result taken just before a write.

A mutation's stamp, when it succeeds, is a snapshot whose time is at or after its commit. On web it is the stamp applied when the mutation's promise continues, which can be a later dispatch than the one that completed it if both arrive in one task: a lower bound, like a native answer whose response arrives late, never an earlier state. That results from that snapshot on show the write rests on the sync protocol, not on the client, so a reader that needs a result to include a write checks both the snapshot and the time against the answer's. When the function fails, the stamp says when this client handled the answer, not which server state the function ran against.

On web, each answer a listener receives inside a transition is recorded as pending; the transition handler, which the JS client calls after the listeners in the same synchronous pass, stamps everything pending with the state it just applied; the answer is handed on a microtask later. Only a listener's first answer may arrive outside a transition: a new listener on a query the client already holds is called from a timer with the value it holds, and takes the stamp of the last transition applied, which is the state that value comes from because counting began before the client held anything. Any later answer that no transition claimed is a fault, and ends that watch with an error rather than be stamped. Our listeners never throw into the JS client's dispatch. One case remains: if another listener throws during a dispatch, the JS client stops calling handlers before ours, and a listener's first answer in that dispatch takes the previous stamp.

A stamped group is handed on only when every member's latest answer was taken on the connection of the newest one. After a reconnect the JS client can drop a member's held value without telling its listener; the group waits until that member answers on the new connection rather than pair an old value with a new one.

## Consequences

- On the stamped calls, a server function's failure is a stamped answer. On web a mutation's is told from a local failure by the exact prefix the JS client builds for it, `[CONVEX M(name)] `, since the bundle offers no public structured way; a query's failure is always a server's, because the JS client reports it only from a result the server sent. `test/collab/live/stamped_transport_live_test.dart` asserts that a refused write comes back as a stamped `NOT_FOUND` on web, so a bundle that changes the text fails it. A failure of the call itself is not an answer: a timeout, arguments that do not convert, a local rejection, or a value that does not decode throws, or ends a watch with that error. A group whose setup fails unsubscribes the members it had already added.
- An empty group is refused on both platforms.
- The web client's stamped one-shot read is a subscription that ends after its first answer, so it is stamped like a live one.
- `test/collab/live/stamped_transport_live_test.dart` checks reads, watches, groups and answers against a local deployment, natively and in Chrome. `test/collab/live/stamped_transport_reconnect_web_test.dart`, in Chrome, closes the socket, holds the new socket's messages and withholds one group member's refresh; it checks that held values handed on after the reopen keep the old connection, and that the group waits for every member on the new one. Both run from `tool/convex_client_gauntlet/runtime/tool/run_with_local_deployment.mjs` in the gauntlet lane. Native reconnects are covered by the Rust client's own tests.
